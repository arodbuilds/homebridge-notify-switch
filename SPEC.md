# homebridge-notify-switch v1 Specification

Status: Draft for review
Repository: https://github.com/arodbuilds/homebridge-notify-switch
Package: homebridge-notify-switch
Author: arodbuilds

## 1. Purpose

A Homebridge dynamic platform plugin that exposes HomeKit switches. Each switch is always off. Turning it on sends one or more preset messages through configured providers and the switch returns to off on its own. Switches are meant to be triggered by HomeKit automations and scenes, giving any HomeKit event a way to notify people by SMS, email, or Telegram.

## 2. Goals and non-goals

### Goals

1. One plugin, multiple channels, one configuration model.
2. Minimum viable setup is a single provider, a single group, a single switch, configurable entirely from the Homebridge UI with no config.json editing.
3. Meets every current Homebridge Verified requirement.
4. Runs comfortably on a Raspberry Pi Zero.
5. Credentials are handled with least privilege and never logged.
6. Configuration shape supports future channels without migration.

### Non-goals for v1

1. Inbound messages or replies.
2. Delivery status callbacks or webhooks.
3. MMS or attachments.
4. WhatsApp (planned for a later version).
5. Fallback routing (send on channel B only if channel A fails). v1 sends on every configured channel in parallel.

Planned for 1.1: WhatsApp via Twilio, using a single approved utility template with the message body as the template variable, so no per-message template approval is needed. Voice calls via Twilio are a candidate for the same release.

## 3. Terminology

1. Provider: a configured connection to an external messaging service. v1 types: `twilio`, `smtp`, `telegram`.
2. Channel: the kind of message a provider can send. v1 channels: `sms`, `email`, `telegram`. The Twilio provider can serve both `sms` and `email`.
3. Recipient group: a named list of people, holding an address list per channel.
4. Switch: a HomeKit switch accessory with one or more actions.
5. Action: one send on one provider, with its own message body, targeting one or more groups and optionally extra individual recipients.

## 4. Platform and accessory model

1. Plugin type: dynamic platform. `pluginAlias` is `NotifySwitch`. `singular` is true (one platform block).
2. Each configured switch becomes one accessory with a `Switch` service.
3. Each switch has a stable `id` (UUID v4 generated by the UI when created; also accepted if typed). The accessory UUID is derived from `id`, never from the display name, so renames do not orphan the accessory in HomeKit.
4. On startup the platform registers accessories for every valid switch and unregisters any cached accessory whose `id` is no longer in config.
5. Optional per switch: a `ContactSensor` service that trips on send failure (see section 9). Default off.
6. Optional platform-level master switch named by the user (default "Notifications Enabled"). When off, no switch sends anything; flips are logged as suppressed. Default enabled and shown.
7. The plugin does not register any accessory if the platform config is missing or fails validation. It logs the reasons and exits its startup path cleanly. It never throws. Cached accessories are left untouched in that case, so HomeKit automations survive a typo.
8. Child bridge is supported and recommended in the README.
9. A configuration that passes validation with zero switches (a fresh install, or after Reset plugin to fresh install in the settings UI) registers nothing and unregisters every cached accessory, the master switch included. The state persisted in their contexts (the master switch position and the failure sensor state) is cleared with them.

### 5.1 Platform fields

1. `name` (string, required). Platform display name.
2. `configVersion` (integer, hidden, default 1). Used for future migrations.
3. `defaultCountry` (ISO 3166-1 alpha-2, default `US`). Used by the UI phone number entry and by startup normalization of numbers lacking a plus sign. The custom UI prefills it on first load from the browser locale, else from the Homebridge host's time zone, else `US` (section 11.2, item 21); startup normalization always uses the saved value, `US` when absent.
4. `masterSwitch.enabled` (boolean, default true). Whether to expose the master switch accessory.
5. `masterSwitch.name` (string, default "Notifications Enabled").
6. `debug` (boolean, default false). Verbose logging; never includes secrets even when on.

### 5.2 Provider fields

Common to all providers: `id` (slug, unique, required), `type` (enum, required), `name` (display name, required).

Twilio (`type: twilio`). Serves channels `sms` and `email`.

1. `accountSid` (required, pattern `^AC[0-9a-fA-F]{32}$`).
2. `apiKeySid` (required, pattern `^SK[0-9a-fA-F]{32}$`).
3. `apiKeySecret` (required, password field).
4. `smsSenders` (array of E.164 strings, `uniqueItems`). At least one of `smsSenders` or `messagingServiceSid` is required to use the `sms` channel.
5. `messagingServiceSid` (optional, pattern `^MG[0-9a-fA-F]{32}$`).
6. `emailFrom.address` and `emailFrom.name` (optional). Required to use the `email` channel. The address domain must be authenticated in the Twilio Console under Communications > Email > Domains.

Auth Token is deliberately not accepted. The README and field help explain that an API key can be revoked without rotating the account's master credential.

SMTP (`type: smtp`). Serves channel `email`.

1. `host` (required).
2. `port` (integer, required, default 465).
3. `security` (enum `ssl`, `starttls`, `none`; default `ssl`). Maps to nodemailer `secure: true`, `requireTLS: true`, and neither, respectively.
4. `username` (required).
5. `password` (required, password field).
6. `from.address` (required, email format) and `from.name` (optional).
7. `smtpPreset` (optional, string). The mail provider preset the custom UI last chose (`fastmail`, `gmail`, `icloud`, `outlook`, `yahoo`, `zoho`), kept for redisplay only (section 11.2, item 22). The runtime never reads it; `host`, `port` and `security` are the settings that count.

No option to disable certificate verification is offered.

Telegram (`type: telegram`). Serves channel `telegram`.

1. `botToken` (required, password field, pattern `^\d+:[A-Za-z0-9_-]{30,}$`).
2. `parseMode` (enum `none`, `markdown`, `html`; default `none`).

### 5.3 Group fields

1. `id` (slug, unique, required).
2. `name` (display name, required).
3. `sms` (array of E.164 strings, optional, `uniqueItems`).
4. `email` (array of email addresses, optional, `uniqueItems`).
5. `telegram` (array of chat IDs matching `^-?\d+$`, optional, `uniqueItems`).

A group with no addresses is valid but produces a startup warning if any switch references it.

### 5.4 Switch fields

1. `id` (UUID, required, generated by the UI).
2. `name` (required). Must satisfy HAP naming: pattern `^[A-Za-z0-9][A-Za-z0-9 ']*[A-Za-z0-9]$`, max 64 characters. Unique across switches.
3. `enabled` (boolean, default true). Disabled switches are still registered but do nothing when flipped, and log the suppression.
4. `cooldownSeconds` (integer, 0 to 86400, default 0). Flips within the cooldown window are logged and ignored.
5. `failureMode` (enum `any`, `all`, `off`; default `any`). Governs when the failure sensor trips and how the result is logged. `any`: any recipient on any channel failing counts as failure. `all`: only when every recipient on every channel fails. `off`: never trips the sensor; failures are still logged.
6. `failureSensor` (boolean, default false). Adds a Contact Sensor service to this accessory. Contact opens on failure and closes on the next successful send or after `failureSensorResetSeconds`.
7. `failureSensorResetSeconds` (integer, default 300).
8. `actions` (array, `minItems` 1).

### 5.5 Action fields

1. `providerId` (required). Must reference an existing provider.
2. `channel` (enum `sms`, `email`, `telegram`, required). Must be a channel the referenced provider serves.
3. `sender` (optional, sms only). One of the provider's `smsSenders`. If omitted and the provider has exactly one sender, that sender is used. If omitted and `messagingServiceSid` is set, the Messaging Service is used.
4. `groups` (array of group ids, optional).
5. `recipients` (array of addresses for this channel, optional).
6. At least one of `groups` or `recipients` must resolve to one or more addresses.
7. `subject` (email only, optional, default is the switch name). CR and LF are stripped.
8. `body` (required). Constraints by channel:
   sms: 1 to 160 characters, GSM-7 character set enforced by pattern in the schema and by validation at startup. The custom UI shows a live character and segment counter.
   email: 1 to 10000 characters. Sent as plain text; HTML is not supported in v1.
   telegram: 1 to 4096 characters. Sent with the provider's `parseMode`.
9. `bcc` (email only, boolean, default false). "Hide recipients from each other (BCC)": when true and the action resolves to more than one recipient, the recipients go in Bcc and the from address in To (sections 6.2 and 6.3). A message to a single recipient always uses To. Set on another channel it is ignored with a startup warning.

### 5.6 Template variables

Available in `body` and `subject`: `{{switchName}}`, `{{time}}` (local HH:mm), `{{date}}` (local YYYY-MM-DD), `{{datetime}}` (local ISO 8601 without zone). Unknown variables are left as typed. The time zone is the Homebridge host's.

## 6. Provider interface

```ts
interface SendRequest {
  channel: Channel;
  sender?: string;
  recipients: string[];
  subject?: string;
  body: string;
}

interface RecipientResult {
  recipient: string;
  ok: boolean;
  id?: string;        // provider message id, operation id, etc.
  error?: string;     // sanitized, no secrets, no request dumps
}

interface Provider {
  readonly id: string;
  readonly type: ProviderType;
  readonly channels: Channel[];
  validateConfig(): ValidationIssue[];
  validateBody(channel: Channel, body: string): ValidationIssue[];
  send(req: SendRequest): Promise<RecipientResult[]>;
}
```

Rules:

1. The switch code imports only this interface. Provider modules are loaded lazily by type so an unused provider costs nothing.
2. Every provider request has a 10 second timeout and at most one retry with a 2 second backoff, except when the provider returns a rate limit response with a retry-after value, in which case that value is honored once.
3. Per-provider in-flight concurrency is capped at 5.
4. Providers never throw. All errors resolve to `RecipientResult` entries. One recipient's failure never stops the others: a provider that sends one request per recipient collects the outcomes with `allSettled` semantics (never `Promise.all`), so a 4xx, a thrown error, or a timeout for one recipient changes that recipient's entry only, and every other recipient is still sent and reported.

### 6.1 Twilio SMS

POST `https://api.twilio.com/2010-04-01/Accounts/{accountSid}/Messages.json` with Basic auth `apiKeySid:apiKeySecret`, form body `To`, `Body`, and either `From` or `MessagingServiceSid`. One request per recipient, concurrency 5. Success is HTTP 201; the `sid` is returned as `id`. Twilio error `code` and `message` are logged.

### 6.2 Twilio Email

POST `https://comms.twilio.com/v1/Emails` with the same Basic auth, JSON body with `from`, `to` (all recipients in one request, so they see each other), and `content.subject` plus `content.text`. With the action's `bcc` option and more than one recipient, the recipients go in `bcc` and the from address in `to`; a single recipient is always in `to`. Success is HTTP 202; `operationId` is returned as `id` for every recipient. One request per action regardless of recipient count.

### 6.3 SMTP

nodemailer transport built from provider config. One message per action with all recipients in `to` by default. With the action's `bcc` option and more than one recipient, the recipients go in `bcc` and the `from` address in `to` (so the envelope is valid and recipients do not see each other); a single recipient is always in `to`. Success is a resolved `sendMail`; the `messageId` is returned as `id`. Rejected addresses reported by the server are mapped to per-recipient failures. nodemailer `debug` and `logger` options are never enabled.

### 6.4 Telegram

POST `https://api.telegram.org/bot{token}/sendMessage` with JSON `chat_id`, `text`, and `parse_mode` when not `none`. One request per chat ID, concurrency 5. Success is `ok: true`; `result.message_id` is returned as `id`. 403 (bot blocked) and 400 (bad chat id) are mapped to readable errors. 429 honors `parameters.retry_after`.

## 7. Runtime behavior on flip

1. HomeKit sets `On` to true. The handler returns immediately.
2. If the master switch is off, or the switch is disabled, or the cooldown is active, log at info and go to step 8.
3. Resolve recipients for each action: union of referenced groups' lists for that channel plus `recipients`, deduplicated.
4. Render template variables.
5. Fire all actions in parallel. Each provider applies its own concurrency cap.
6. Collect results. Log one line per recipient (see section 8) and one summary line per switch.
7. Evaluate `failureMode` and update the failure sensor if enabled.
8. After 1 second, set `On` back to false and notify HomeKit.

Setting `On` to false from HomeKit is a no-op.

## 8. Logging

1. Info on each send: `[Water Leak Alert] sms via twilio-main to +1678***0101: sent (SM...)`. Phone numbers and email addresses are partially masked in info logs; full addresses appear only when `debug` is true.
2. Warn on each failure with the provider's error code and a short message.
3. Error only for configuration problems at startup.
4. Message bodies are never logged at info. With `debug` true, bodies are logged.
5. Secrets are never logged at any level. Error objects from providers are reduced to code and message before logging.

## 9. Failure sensor

1. Service type `ContactSensor`, `ContactSensorState` open (1) means a failure occurred.
2. Trips according to `failureMode`.
3. Resets to closed on the next fully successful send from that switch, or after `failureSensorResetSeconds`.
4. Exposed on the same accessory as the switch so it shares the room and name.

## 10. Startup validation

Validation runs in code, independent of the schema, and reports every issue in one pass with the field path, for example `switches[2].actions[0].providerId: no provider with id "twillio-main" (did you mean "twilio-main"?)`.

Blocking issues (the platform registers nothing and cached accessories stay): invalid provider credentials format, invalid or duplicate ids, a switch with no resolvable recipients, a body that violates channel constraints, a provider type that does not serve the requested channel, a switch name that violates HAP naming, an action that references a provider or group that does not exist.

An empty `providers` or `switches` list is not an error. No switches means nothing is registered and every cached accessory is removed (section 4, item 9); it is logged as a warning.

Warnings (the platform starts): no providers, no switches, a group with no addresses, a provider that no switch uses, a sender not in the provider's list when only one sender exists (it is used anyway), and a switch that targets a group holding addresses on a channel none of its actions send on (an uncovered channel; logged once per switch and channel with the switch name, the group ids and the channel, because those people receive nothing).

Phone numbers without a leading plus sign are normalized using `defaultCountry`; the normalized value is logged once at startup so the user can correct config.json if desired.

## 11. Settings UI

### 11.1 Schema form

`config.schema.json` is complete on its own so the plugin remains configurable if the custom UI fails to load. It uses `headerDisplay` for the getting-started text, section `description` fields, per-field `description` help, `x-schema-form` password types for secrets, and `condition` rules so provider fields appear only for the selected type.

### 11.2 Custom UI

Built with `@homebridge/plugin-ui-utils`. Replaces the schema form with a three-section page: Providers, Recipient Groups, Switches. It reads and writes the same config object.

Additional behavior beyond the schema form:

1. Phone number entry: country dropdown (flag, name, dial code) defaulting to `defaultCountry`, and a national number field with a local placeholder. Nothing is reformatted while the field has focus; it accepts digits, spaces, dashes, dots, parentheses, and a leading plus (other characters are dropped as typed, the caret stays in place). On blur the text is parsed with libphonenumber-js using the selected country as the hint, stored as E.164, the country is re-derived from the parsed number (a +1 305 number selects United States even if Canada was selected) and the dropdown updated, and the field shows the national format. The "Stored as +…" line appears only when parsing succeeds; otherwise an inline error is shown and the raw text is kept. Changing the country re-parses the current text. Applies to every phone field: provider sender numbers, group SMS lists, and extra SMS recipients.
2. SMS body: live character count, segment count, and a warning when a non-GSM-7 character is present with the offending character highlighted.
3. "Test connection" per provider: SMTP runs nodemailer `verify()`; Twilio lists one message (GET `/2010-04-01/Accounts/{accountSid}/Messages.json?PageSize=1` with the API key pair, so Restricted keys scoped to Messaging pass as well as Standard keys); Telegram calls `getMe`. Twilio failures include Twilio's error code and message when the response carries them. Credentials from the form are used in memory only and never returned or written.

7. Reference pickers: provider and group selectors are dropdowns populated from the current config, not free text.
8. Uncovered channel warnings: for each switch, the channels present in the groups (and extra recipients) it targets are compared with the channels its actions cover. Each uncovered channel shows a warning on the switch card (copy in section 11.3) with an "Add … action" button, worded per channel, that appends an action for that channel with the first provider that serves it preselected and the targeted groups that hold addresses on that channel selected. 14. Hidden ids: provider and group ids are generated from the name and never shown in the main form. Each card's "Advanced" disclosure holds the ID read-only with an "Edit" text button that makes it editable, for people who hand-edit config.json; one-sentence help reads "How switches refer to this provider in config.json." (or group). Format and uniqueness are still validated with the same messages, and an issue on the ID opens the disclosure so it is never invisible. A generated id keeps following the name as it is typed until it is edited by hand or a switch action refers to it, so renaming a provider or group never breaks a switch. A new group starts as `group` (then `group-2`) until it is named. Switch ids stay UUIDs (item 6) and are shown as before.
15. Per-field validation. Touched state is tracked per field, not per card: a field is touched when its control loses focus, when a select, checkbox or radio in it changes, or when its entry in the issue list is used to jump to it (typing alone does not count). A field shows its error inline only once it is touched. Cross-field checks belong to every field they read and appear inline once any of those fields is touched: recipient coverage ("Nobody would receive this action") to the action's Groups checkboxes and its extra recipients list, a duplicate switch name to both name fields, a duplicate or invalid id to the card's Name field as well, a provider-dependent channel or sender check to the Provider dropdown, and "Add at least one action" to the switch's Name field. While a field has an error showing, input re-validates only to clear it; an error is never added while the field has focus, it appears when the field is left. This applies to every field, list entries (phone numbers, email addresses, chat ids) and action fields included. A touched field that passes validation and holds a value shows a small green check inside the control. Validation messages render on their own line below the field or list row, never in a flex row with inputs or buttons, and an input never changes width or wraps when a message appears or disappears; a browser test types into an email entry and a phone entry and asserts the input's bounding box is unchanged after the error appears. A provider, group or switch added in this session is fresh: its card shows placeholders and no errors, and its issues are left out of the issue list, until a field in it is touched. ## 12. Security

1. Credentials are stored in config.json like every Homebridge plugin. The README states that Homebridge UI backups contain config.json and should be treated as containing secrets.
2. Optional `credentialsFile` on any provider: a path relative to the Homebridge storage directory pointing to a JSON file whose keys override the provider's secret fields. Keeps secrets out of config.json, backups, and screenshots. Inline remains the default.
3. Twilio accepts API keys only. SMTP help steers users to app passwords. Telegram tokens are bot-scoped by nature.
4. No credential, message body (at info level), or raw provider error object is ever logged.
5. Custom UI server endpoints use submitted credentials in memory only, never persist or echo them, and only connect to the host the user configured.
6. TLS verification cannot be disabled.
7. Email subject and from name have CR and LF stripped. Telegram defaults to plain text.
8. Cooldown and master switch limit abuse from runaway automations.
9. Dependencies: nodemailer at runtime; libphonenumber-js and qrcode-generator in the UI bundle; everything else dev-only. `package-lock.json` is committed. Dependabot is enabled.
10. Publishing uses GitHub Actions with npm trusted publishing and provenance after the first release. Branch protection on `main` requires a pull request.

2. `engines.node`: `^22.12.0 || ^24.0.0`. `engines.homebridge`: `^1.6.0 || ^2.0.0`.
3. `keywords` include `homebridge-plugin`. `displayName` is "Notify Switch".

## 15. Open questions for review

1. Should `emailFrom` on the Twilio provider default to nothing, or should the UI prompt for it when the user adds an email action on a Twilio provider? Proposal: prompt in the UI, leave the field optional in schema.
2. Should the master switch be on by default? Proposal: yes, exposed and enabled, because most users will want a single kill switch in Home.
3. Failure sensor reset: time-based only, or also reset when the switch is flipped again regardless of outcome? Proposal: reset only on success or timeout.
4. Should v1 accept `html` for email bodies? Proposal: no; plain text keeps the UI simple and avoids injection concerns.
5. Node 20 in the engines field: keep for broad compatibility, or drop since the template now requires 22? Proposal: drop, matching the template and Homebridge v2 guidance.
